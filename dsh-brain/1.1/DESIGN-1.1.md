# dsh-brain 1.1 设计 · 任务封存（Seal）

> 目标：**记忆是本体，会话是工作台。** 每完成一个任务就封存一次：把上下文炼成卡片，关掉旧工作台，开一个干净的。
> 本文件是创作模式的唯一依据；在 1.0 基础上增量修改，不改动已有的自动接续逻辑。

## 一、为什么要做

1.0 的接续是"快满了才跑"（80% / 150k / 60 轮），太晚。实测会话上下文能涨到 **36 万 token**，之后每次请求都在为历史付费（约 ¥0.014/次）。

1.1 把封存点前移到**任务边界**：一件活干完就封存，新会话上下文只有 1 万左右，单次请求降到 **¥0.001–0.004**。

## 二、核心概念

| 概念 | 说明 |
|---|---|
| **工作台** | 会话本身：临时、可丢弃、只承载"这次任务" |
| **本体** | 记忆卡片：画像、项目卡、任务卡、日记 |
| **封存（Seal）** | 把一个任务的全部状态写成卡，然后开新会话 |
| **任务边界** | 由 agent 判定（它知道活干完没有），不是靠猜文字 |

## 三、触发方式

| 方式 | 优先级 | 说明 |
|---|---|---|
| agent 调用 `task_seal` 工具 | 主路径 | 任务收尾时主动调用，参数由 agent 填写 |
| 面板按钮「封存并开新会话」 | 手动 | 用户觉得该换了就点 |
| 用户说「封存 / 新话题」 | 手动 | 解析为调用 `task_seal`（无参时 agent 自动补内容） |
| 现有阈值接续 | 兜底 | 80% / 150k / 60 轮，保留不变 |

**不做**：文字相似度猜话题、自动无提示切换。

## 四、任务卡（防细节丢失的核心）

封存时写 `实时记忆\当前任务.md`，结构固定、上限 **800 字**：

```markdown
# 当前任务

**封存于**：2026-10-24 11:40 · 来自会话 <id 前 8 位>

## 任务
<一句话：这次在干什么>

## 已完成
- <3–6 条，每条 ≤40 字，带结果>

## 关键决定
- <为什么这么做，备选是什么，为什么不选>

## 涉及文件
- `<绝对路径>` —— <改了什么>

## 下一步
- <1–3 条，可直接执行>

## 坑
- <这次踩到的，避免重蹈>

## 恢复步骤
```powershell
<关键命令，新会话照着跑就能回到现场>
```
```

写入规则：
- 由 `task_seal` 的参数拼装，**agent 负责摘要**，插件只做格式与截断；
- 超 800 字按「任务 > 已完成 > 下一步 > 关键决定 > 坑 > 文件 > 恢复步骤」优先级截断；
- 写卡成功但建会话失败时，卡片保留并标注 `**封存失败**：原因`。

## 五、新会话的注入
首步注入顺序（总预算 ≤1500 字）：

1. 用户画像（baseline，沿用 1.0，≤1300 字）；
2. 当前工作区概况摘要（≤120 字）；
3. **任务卡全文**（≤800 字，取代原来的 300 字实时卡）；
4. 之后每轮仍是 BM25 top-2、单卡 ≤600 字。

实现要点：`inject.js` 里判断"本会话是否由封存创建"（读 state 的 `sealedFrom`，或任务卡里 `来自会话` 与当前 id 不同），是则强制注入任务卡，不走检索。

## 七、安全与失败处理

**拒绝封存的条件**（任一即拒绝，返回错误给 agent）：
1. 有未完成的工具调用；
2. 上一条 assistant 消息含未完成的 tool_call；
3. 会话轮次 < 2（几乎没内容，封存没意义）。

**失败处理**：

| 情况 | 处理 |
|---|---|
| 写卡失败 | 中止，旧会话不变 |
| 建会话失败 | 卡片保留并标 `封存失败`，旧会话不变，返回错误 |
| 继承模型/权限失败 | 新会话照用，日志记警告，toast 提示 |
| 归档失败 | 不阻塞 |
| 连续调用 seal | 会话级锁，5 秒内只允许一次 |

**不做**：不删除任何会话；不代发首条消息；不在生成中切换。

## 八、验收标准

1. 让 agent 在完成任务后调用 `task_seal`，新会话出现，且**第一条回复能说出刚才干了什么、下一步是什么**；
2. 新会话首次请求 input ≤ 12k token；
3. 模拟 create 失败：旧会话可用，任务卡带 `封存失败` 标记；
4. 旧会话出现在「已归档」，可取消归档；
5. 连续点两次按钮，只封存一次；
6. 在有未完成工具调用时调用 `task_seal`，被拒绝且给出原因。

## 九、成本

| 项 | 每次 |
|---|---|
| 写任务卡（agent 输出 ~800 字） | ≈ ¥0.0006 |
| 新会话首请求（~10k input） | ≈ ¥0.0015 |
| 归档 / 建会话 | 0 |
| **合计** | **≈ ¥0.002（两厘）** |

对比：在 36 万上下文的会话里继续，每次请求约 ¥0.014。**封存后每 10 次请求省下的钱，够封存 5 次。**

## 十一、会话摘要（保真层，必须做）

封存时除任务卡外，**再写一份长摘要**，落在 `工作记忆\实时记忆\日志\会话摘要\<YYYYMMDD-HHmm>-<任务名>.md`：

```markdown
# 会话摘要 · <任务名>

- 时间：<开始> – <结束>
- 来源会话：<id 前 8 位>
- 模型：<provider/model>

## 原始需求
<用户原话，至少一条完整句>

## 过程
<按时间列：做了什么 → 结果；关键命令原文；关键输出片段>

## 错误与纠正
<报错原文 + 怎么修的>

## 最终方案
<落地的东西：文件、配置、决定>

## 回滚方法
<具体命令>
```

规则：

- **不限长度**，宁可啰嗦；它不注入，不占上下文；
- 只追加，不改写；同名任务重复封存时加序号；
- 任务卡放「结论」，摘要放「过程与原文」——两者互补，缺一不可；
- 摘要写入失败不阻塞封存，但要在任务卡里标 `摘要缺失`。

验收追加一条：封存后 `日志\会话摘要\` 下确实出现文件，且含原始需求与回滚方法。
